# Working in this repository

Private systematic trading research for CME Gold futures (GC, and MGC as the intended execution instrument). This is a **research** codebase, not an application. Its value is the trustworthiness of its conclusions, so the rules below take priority over speed, tidiness, and cleverness. Read `README.md` for structure and `project_docs/` for the governing reports.

## The rules that matter most

**Never let a result influence a decision that should have preceded it.** Research questions, thresholds, horizons, populations, and acceptance criteria are declared in a frozen contract under `project_docs/*_research_contract.md` *before* anything is computed. If a contract is ambiguous (for example it says "the primary horizon" without naming one), do not resolve the ambiguity yourself after seeing output — record it and ask the contract owner for an amendment. Choosing after the fact voids the run, and the contracts say so explicitly.

**The final-test partition is not a data source.** Partitions are Development (through 2023), Validation (2024), and Final test (2025 onward). Fit and select on Development, confirm on Validation. The final-test partition is read once, after verdicts are already fixed, and never explored descriptively — not even for a summary table or a plot. Excluding it is a correctness requirement, not a style preference.

**Never commit market data or generated artifacts.** `.gitignore` is the data-governance boundary. Parquet tables, figures, CSVs under `reports/**/tables/`, and raw Databento files stay local. Tracked markdown summaries are the record of results; do not force-add ignored files to make a document's claim true — fix the document.

**Do not quietly change frozen research code.** Modules underpinning merged verdicts (Sections 6 through 12B, the POI research chain) produce artifacts that published conclusions rest on. Refactoring them for elegance is not worth invalidating a result. If a change is genuinely required, say what it does to the artifacts.

**A negative result is a result.** Most hypotheses here have been rejected, and that is the point. Never tune toward a positive finding, and never soften a rejection in a summary.

## Determinism and portability

Contributors run on materially different hardware (a CPU-only 8 GB laptop and a 32 GB workstation with a 4 GB NVIDIA GPU). Both must produce identical research numbers.

- `src/compute.py` resolves the compute backend. `PROJECT_COMPUTE=auto|cpu|gpu` overrides detection; `cpu` makes a GPU host reproduce a CPU-only host exactly.
- **Research-artifact numerics stay on the deterministic CPU path.** Floating-point reductions are not associative, so a GPU scan and a CPU scan can disagree in the last bits. Do not add device dispatch to code that produces a frozen artifact. CPU parallelism is acceptable only where work splits into independent units and input order is restored (`parallel_map`).
- Never wrap numerical code in a bare `except Exception` with a fallback path. A silent fallback that returns slightly different numbers is the worst possible failure here.
- The numerical stack (numpy, pandas, scipy, pyarrow) is pinned to exact versions in `requirements.txt`, because committed feature-matrix values have been observed to differ between NumPy builds on identical input. The notebook verifies these pins at startup and fails loudly. Do not relax a pin to a floor.
- Plan work against memory, not core count — see `src/resources.py` (RAM tiering, chunking) and `plan_batches` in `src/compute.py`.
- Use repository-relative paths everywhere. No absolute paths in source, notebooks, or docs.

## Environment and verification

```powershell
python -m venv .venv                         # any venv name inside the repo works
python -m pip install -r requirements.txt    # add -r requirements-gpu.txt only if CUDA is present
python -m unittest discover -s tests         # the suite is unittest; pytest is not used
python -m ruff check . ; python -m ruff format .
```

Before claiming anything works: run the full test suite and ruff. For research changes, execute the affected notebook end to end with nbconvert (roughly 20 minutes) and confirm every gate still prints `STATUS: READY`. Gates assert integrity only — never make a gate assert a particular research outcome.

Notebook sections are generated by `scripts/update_*_notebook.py` and then executed in place. Summaries for Sections 5 and 6 are **regenerated by notebook runs**, so hand edits there are overwritten; Sections 7 onward are hand-authored tracked records. Do not put volatile values (wall-clock timings, memory readings) into a tracked summary — they create churn on every rerun.

## Collaboration

- Branch per milestone, PR to `main`, delete the branch after merge. Never touch a branch you did not create.
- **No AI attribution trailers in commits or PR bodies** — no `Co-Authored-By` for an assistant, no "Generated with" footers.
- No emojis or logos anywhere in code, commits, or documentation.
- Keep documentation concise and non-repetitive. History is never rewritten; current state must always be discoverable, so append status addenda rather than editing past records.

## Optional tooling: GitNexus

This project may be indexed by GitNexus, which exposes `gitnexus_*` MCP tools for symbol impact analysis and call-graph-aware navigation. It is a **local, optional** developer aid — nothing in this repository requires it, and the tools are often not connected. When they are unavailable, use ordinary search and reading.

Run `npx gitnexus analyze` if a tool reports a stale index.

Two caveats specific to this repository:

- The `.claude/` directory is git-ignored, so the skill files GitNexus references are not shared between contributors. If the team wants this as a common workflow, track `.claude/skills/` deliberately.
- Impact analysis reports *structural* risk. It cannot see the risk that actually matters most here — that a change alters a frozen research artifact. A green blast radius is not permission to modify frozen research numerics.
