## Leakage verification

Parameters are estimated on Development bars only and frozen; the recursion is applied forward using only prior information; the regime threshold is a Development-only quantile. This is asserted two ways. `tests/test_garch_volatility.py` perturbs final-test prices in a synthetic frame and requires every earlier conditional-volatility and regime value to be bit-identical, and separately requires the threshold to be unmoved when all non-Development prices are scaled. The same perturbation check was then run against the full 3,487,656-bar dataset and passed: **earlier bars identical = True**.

## Defects corrected

- **Recursion seeding.** The original notebook implementation seeded `sigma2[0]` with the *last* Development bar's conditional volatility while applying the recursion from the *first* bar of the series. The seed is now the Development return variance — a Development-only quantity, and the appropriate choice here because a boundary fit makes the long-run variance `omega / (1 - alpha - beta)` undefined or negative. The practical effect on values is small (beta near 0.9 decays the seed within roughly ten bars) but the stated method and the executed method now agree.
- **Inaccurate comment.** A comment described the recursion as "numpy-vectorised, no Python loop" while the code was a Python loop over 3.5 million rows. The GARCH recursion is sequential by definition — `sigma2[t]` requires `sigma2[t-1]` — so it cannot be vectorised across time. The claim was removed rather than the loop.
- **Premature final-test exposure.** The regime summary grouped by partition including `final_test`, before any verdict existed. Summaries are now restricted to Development and Validation, and the notebook gate asserts that the final-test partition does not appear.

Fitting plus the forward recursion over all 3,487,656 bars takes about 24 seconds.

## Why H1 and H2 are not evaluated

Two blockers are recorded rather than resolved, because resolving either changes what the frozen contract means. Both belong to the contract owner.

**1. The primary research horizon is not pinned.** H1 is stated "at the primary research horizon", but six are available (`forward_return_{5,15,30,60,120,180}_atr`). Selecting one after fitting results are visible is precisely the degree of freedom the contract's own voiding clause exists to prevent ("any threshold change, horizon change, or subgroup definition change after seeing results voids the run"). The horizon needs to be declared as a contract amendment before evaluation.

**2. The fitted model is a boundary solution, not a valid stationary fit.** GC fits at persistence **1.000327** with the optimizer reporting non-convergence; MGC fits at **1.000001**. Both are at or above the stationarity limit, so the conditional variance process is integrated-to-explosive and has no unconditional variance. Contract H3 as written ("alpha + beta > 0.90, informational only") would read as a pass here, which would be misleading: the criterion was designed to confirm the well-known high persistence of futures volatility, not to bless a degenerate fit.

This outcome is expected when GARCH(1,1) is fitted directly to one-minute bars. Intraday volatility follows a strong repeating diurnal pattern, and a model with no seasonal term absorbs that pattern into persistence, driving alpha + beta to the constraint boundary. Evaluating H1 or H2 on this fit would attribute economic meaning to a specification artifact.

The standard remedies — deseasonalising returns before fitting, fitting at a coarser frequency, or imposing variance targeting — are all changes to the frozen model specification, and therefore contract amendments rather than implementation choices.

## Recommended next step

Amend the contract to (a) name the primary research horizon explicitly and (b) replace the plain GARCH(1,1)-on-1-minute-bars specification with one that accounts for intraday seasonality, re-freeze it, then evaluate H1 and H2. Until then the feature is available for diagnostic use, and no risk-conditioning claim may rest on it.

**No volatility-regime effect on forward returns has been demonstrated.** This document records an implemented, leakage-safe feature and a fit-quality failure, nothing more.
